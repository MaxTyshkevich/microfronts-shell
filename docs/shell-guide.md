# Руководство по работе с Shell

Карта текущего локального проекта и план его развития. Технические правила: [архитектура](architecture.md), [конфигурация](runtime-config.md), [процесс работы](../AGENTS.md).

## Что принадлежит Shell

Shell запускает приложение, управляет навигацией, сессией и подключением независимых микрофронтов. Товары и операции корзины принадлежат Catalog и Cart; создание сессии и проверка прав на данные — backend.

Слои: app → pages → entities. app соединяет части приложения; pages содержит собственные страницы; entities/session — модель сессии и запросы. Страницы получают host-данные через props и не импортируют app. Исходники соседних репозиториев не импортируются.

HostProvider только подключает общий клиент. Router определяет доступ и соединяет страницы с сессией. AuthenticatedQueryProvider владеет кешем закрытой части приложения. Маленький app.tsx оставляет понятную точку сборки приложения. RemoteBoundary изолирует обработку ошибок React. Два CSS-файла подключают reset и Tailwind; оформление элементов задано классами в разметке.

## Порядок запуска приложения

1. main.tsx подключает CSS и отображает App.
2. Модуль App регистрирует remote и создаёт router вне рендера React.
3. HostProvider предоставляет общий QueryClient. ShellLayout и guards используют один запрос /auth/me через useSession.
4. ShellLayout собирает хедер, основное содержимое с Outlet и футер, не блокируя публичные страницы. После выхода открывается главная.
5. Router применяет правила доступа. Remote загружается при его отображении.

Неверные URL останавливают запуск Vite или сборку. Запроса конфигурации в браузере нет. Ошибки API и remote обрабатываются внутри приложения.

## Маршруты, сессия и роли

| Маршрут | Доступ |
| --- | --- |
| /, /login, /register | Гости; подтверждённый пользователь переходит на returnTo или /catalog |
| /catalog, /cart, /account | Только подтверждённые пользователи; гость переходит на login с адресом возврата |
| Неизвестный URL | 404 |

Главная и формы остаются доступными при ожидании и ошибке /me. Закрытые маршруты в этих случаях показывают ожидание или повторную проверку, без загрузки remote. Меню гостя содержит главную/вход/регистрацию, меню пользователя — каталог/корзину/аккаунт/выход. После выхода открывается главная.

В router.tsx GuestOnly управляет гостевыми страницами, RequireAuth — всеми закрытыми. AccountRoute передаёт пользователя странице через props; AuthPage получает только mode и api. RemoteRoute сохраняет существующий контракт remote: API, QueryClient, user:<id>, callbacks и пустой cartKey. Backend выбирает корзину по cookie, поэтому гостевой ключ не нужен. Никаких гостевых UUID или записей localStorage Shell не создаёт.

`entities/session/api/session-api.ts` содержит HTTP-функции. `session-queries.ts` описывает получение /me, `session-mutations.ts` — вход/регистрацию/выход и кеш. Хуки сценариев в pages/auth/model и app/model добавляют переходы. Пользователь хранится только в Query; HostProvider не хранит собственную сессию и не предоставляет host-контекст.

Login/register устанавливают HttpOnly cookie и возвращают {success: true}; затем /me подтверждает пользователя и роль. Перед применением результатов мутации старые запросы /me отменяются. Отсутствие cookie или user: null означает отсутствие входа; ошибка сети не означает гостя. returnTo ограничен /catalog, /cart и /account, по умолчанию открывается каталог.

RequireAuth подключает отдельный AuthenticatedQueryProvider для данных remote с key по user.id. Выход, ошибка/сброс сессии или смена пользователя размонтируют дерево и очищают этот клиент; запоздалые ответы и мутации не попадают в новый кеш. Запрос сессии остаётся во внешнем QueryClient. onUnauthorized от remote перепроверяет /me до повторного показа закрытых данных.

USER и ADMIN имеют одинаковый доступ к существующим закрытым страницам. Неизвестная роль считается ошибкой сессии. Новые роли и административные страницы требуют отдельного согласования и серверных проверок.

## Ежедневная работа

Из apps/shell при установленных зависимостях и доступной настроенной базе данных:

```powershell
npm run dev:all
```

Текущая команда запускает Shell, Catalog, Cart и backend. Открыть http://localhost:5173. Она не запускает PostgreSQL и не выполняет миграции. Если backend уже работает отдельно, не запускайте второй экземпляр: используйте npm run dev для Shell и dev:remote в нужных remote.

npm ci нужен для первой установки или синхронизации с изменённым lock-файлом. Он устанавливает зафиксированные версии, а не обновляет библиотеки до последних. Для обычного запуска повторять установку не нужно. Сам Shell устанавливается независимо; dev:all требует соседних репозиториев по путям из package.json.

## Где делать изменения

| Задача | План действий |
| --- | --- |
| Изменить форму входа | pages/auth; изменение HTTP-контракта — entities/session; кеширования — entities/session/api; доступа — router.tsx |
| Добавить страницу Shell | pages/<имя>/ui и публичный index.ts; маршрут в router.tsx; явно выбрать доступ |
| Добавить пункт меню | shell-header.tsx; проверить прямой URL и guard в router.tsx |
| Добавить remote | Согласовать props в contracts; обновить конфигурацию окружения и её проверку в Vite, реестр и маршруты; проверить отказ загрузки |
| Изменить товары/корзину | Соответствующий независимый репозиторий; Shell менять при изменении интеграции |
| Изменить стили | shell: utilities в JSX; общие компоненты — UI-пакет |
| Сменить URL API/remote | Переменные Vite; инструкция в runtime-config.md |

## План развития и упрощения

1. **Сохранять разделение доступа.** Проверять гостевые и закрытые маршруты, недоступность API и изоляцию аккаунтов при каждом изменении авторизации.
2. **Назначать владельца каждого изменения.** Оболочка, страница, сессия или remote. Критерий: бизнес-логика каталога и корзины не попадает в app.
3. **Уточнять права при появлении функций.** Перед административными страницами согласовать матрицу доступа и контракт роли. Проверить гостя, USER, ADMIN, прямой URL и отказ backend.
4. **Не возвращать лишние обёртки.** Технические параметры старого контракта remote остаются в RemoteRoute; общие настройки клиентов — в query-client. Новый файл оправдан самостоятельной обязанностью, повторным использованием или облегчением чтения. Настройки queryOptions/mutationOptions и обновление сессии находятся в entities/session/api, навигация после мутаций — в хуках модели владельца (pages/auth и app); JSX не содержит описание запросов.
5. **Делить крупные модули по мере роста.** Если подключение новых remote перегрузит router, вынести RemoteRoute. Если появятся несколько самостоятельных правил доступа, выделить guards. Сейчас небольшие компоненты оставлять рядом с деревом маршрутов. Не делать переносы только ради количества строк или папок.
6. **Поддерживать поведение проверками.** При изменении авторизации проверять прямые ссылки, ошибки API, потерю сессии и смену пользователя. При изменении ответственности модулей обновлять архитектуру и это руководство.

Это последовательность дальнейшей работы; перечисленные будущие шаги не считаются выполненными автоматически.

## Проверки и завершение

Для изменений кода из apps/shell:

```powershell
npm run typecheck
npm run check:architecture
npm run build:local
npm run test:auth
```

`npm run test:auth` запускает `pages/auth/ui/auth-page.pw.spec.ts` и `app/routes/router.pw.spec.ts`: формы, маршруты, returnTo, выход, потерю сессии и изоляцию аккаунтов. Подменяются HTTP-ответы и адаптер federation; backend, база данных и настоящие remote не запускаются. При изменении серверного контракта дополнительно нужны интеграционные проверки с настоящим backend.

Для Markdown проверить пути, соответствие коду, UTF-8 и git diff --check. Перед commit просмотреть diff и включить только изменения задачи. В PR описать проблему, итоговое поведение, фактические проверки и ограничения. Последующие коммиты той же задачи отправлять в его ветку. Историю задач хранить в Git/PR; руководство описывает устройство проекта и рабочий процесс.
