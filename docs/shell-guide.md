# Руководство по работе с Shell

Карта текущего локального проекта и план его развития. Технические правила: [архитектура](architecture.md), [конфигурация](runtime-config.md), [процесс работы](../AGENTS.md).

## Что принадлежит Shell

Shell запускает приложение, управляет навигацией, сессией и подключением независимых микрофронтов. Товары и операции корзины принадлежат Catalog и Cart; создание сессии и проверка прав на данные — backend.

Слои: app → pages → entities. app соединяет части приложения; pages содержит собственные страницы; entities/session — модель сессии и запросы. Страницы получают host-данные через props и не импортируют app. Исходники соседних репозиториев не импортируются.

## Карта app

Сейчас в app 10 файлов: 8 модулей TypeScript/TSX и 2 CSS-файла.

| Файл | Ответственность | Когда менять |
| --- | --- | --- |
| [entrypoint/app.tsx](../src/app/entrypoint/app.tsx) | Соединяет конфигурацию, remote, router и HostProvider один раз при запуске | Добавление общего provider, изменение порядка запуска |
| [config/config.ts](../src/app/config/config.ts) | Предоставляет адреса API и remote из import.meta.env | Изменение схемы конфигурации и правил URL |
| [providers/host-provider.tsx](../src/app/providers/host-provider.tsx) | Сессия, QueryClient, гостевой ключ, смена пользователя и восстановление сессии | Изменение жизненного цикла авторизации или изоляции кеша |
| [routes/router.tsx](../src/app/routes/router.tsx) | Дерево URL, правила доступа, передача host-данных страницам и remote | Добавление маршрута, изменение доступа или интеграции |
| [ui/shell-layout.tsx](../src/app/ui/shell-layout.tsx) | Навигация, выход, место вывода страницы через Outlet | Изменение меню и общего каркаса |
| [integrations/remotes/register-remotes.ts](../src/app/integrations/remotes/register-remotes.ts) | Регистрация URL, ленивые компоненты, таймаут загрузки | Подключение нового микрофронта |
| [integrations/remotes/remote-boundary.tsx](../src/app/integrations/remotes/remote-boundary.tsx) | Изоляция ошибок remote и сообщение о восстановлении | Изменение обработки ошибок загрузки/рендера |
| [lib/guest-cart-key.ts](../src/app/lib/guest-cart-key.ts) | Создание, проверка и хранение гостевого ключа, обработка недоступного localStorage | Изменение хранения ключа; это не токен входа |
| [styles/page-reset.css](../src/app/styles/page-reset.css) | Глобальный reset из UI-пакета | Изменение базового оформления всей страницы |
| [styles/tailwind.css](../src/app/styles/tailwind.css) | Tailwind с префиксом shell: и сканированием своего src | Настройка генерации utilities |

Основная сложность находится в host-provider.tsx и router.tsx. Объединять их ради уменьшения числа файлов не стоит: управление сессией и выбор страницы имеют разные обязанности. Маленький app.tsx оставляет понятную точку сборки приложения. RemoteBoundary изолирует обработку ошибок React. guest-cart-key.ts отделяет детали localStorage от переходов сессии. Два CSS-файла подключают reset и Tailwind; оформление элементов задано классами в разметке.

## Порядок запуска приложения

1. main.tsx подключает CSS и отображает App.
2. Модуль App регистрирует remote и создаёт router вне рендера React.
3. HostProvider предоставляет QueryClient и запускает проверку /auth/me.
4. ShellLayout показывает навигацию и Outlet, не блокируя публичные страницы.
5. Router применяет правила доступа. Remote загружается при его отображении.

Неверные URL останавливают запуск Vite или сборку. Запроса конфигурации в браузере нет. Ошибки API и remote обрабатываются внутри приложения.

## Маршруты, сессия и роли

| Маршрут | Доступ |
| --- | --- |
| /login, /register | Без сессии, во время её загрузки и при ошибке API. Подтверждённый пользователь переходит на безопасный returnTo или /account |
| /catalog, /cart | Гости и пользователи после определения сессии, чтобы выбрать правильную корзину и кеш |
| /account | Подтверждённый пользователь; гость переходит на login с адресом возврата |
| Неизвестный URL | Публичная страница 404 |

В router.tsx GuestOnly управляет формами, SessionBoundary показывает ожидание/ошибку сессии, RequireAuth защищает аккаунт. AuthRoute и AccountRoute передают данные страницам. RemoteRoute передаёт API, QueryClient, область сессии и callbacks микрофронтам.

И login, и register создают сессию. Backend устанавливает HttpOnly cookie и возвращает {success: true}; затем Shell получает пользователя и роль через /auth/me. Cookie отправляет браузер, JavaScript не читает токен. Подтверждённый гость — ответ user: null; ошибка сети не означает гостевую сессию.

При смене пользователя HostProvider заменяет QueryClient и очищает старый кеш, чтобы не показывать чужую корзину. Первоначальное подтверждение гостя не перемонтирует уже заполняемую форму.

USER и ADMIN сейчас имеют доступ к аккаунту; административных страниц нет. Неизвестная роль считается ошибкой сессии. При добавлении административной страницы сначала определить разрешённые роли и серверные проверки, затем добавить guard и меню. Скрытый пункт меню не защищает API. Сейчас SessionUser расширяет общий User локально; перенос role в contracts потребует согласованного выпуска пакета и потребителей.

## Ежедневная работа

Из apps/shell при установленных зависимостях и доступной настроенной базе данных:

```powershell
npm run dev:all
```

Текущая команда запускает Shell, Catalog, Cart и backend. Открыть http://localhost:5173. Она не запускает PostgreSQL и не выполняет миграции. Если backend уже работает отдельно, не запускайте второй экземпляр: используйте npm run dev для Shell и dev:remote в нужных remote.

npm ci нужен для первой установки или синхронизации с изменённым lock-файлом. Он устанавливает зафиксированные версии, а не обновляет библиотеки до последних. Для обычного запуска повторять установку не нужно. Сам Shell устанавливается независимо; dev:all требует соседних репозиториев по путям из package.json.

## Где делать изменения

| Задача | План действий |
| --- | --- |
| Изменить форму входа | pages/auth; изменение HTTP-контракта — entities/session; жизненного цикла — HostProvider |
| Добавить страницу Shell | pages/<имя>/ui и публичный index.ts; маршрут в router.tsx; явно выбрать доступ |
| Добавить пункт меню | shell-layout.tsx; проверить прямой URL и guard в router.tsx |
| Добавить remote | Согласовать props в contracts; обновить конфигурацию окружения и её проверку в Vite, реестр и маршруты; проверить отказ загрузки |
| Изменить товары/корзину | Соответствующий независимый репозиторий; Shell менять при изменении интеграции |
| Изменить стили | shell: utilities в JSX; общие компоненты — UI-пакет |
| Сменить URL API/remote | Переменные Vite; инструкция в runtime-config.md |

## План развития и упрощения

1. **Зафиксировать текущую авторизацию.** Просмотреть локальный diff, отделить предыдущую работу Tailwind и оформить изменения в соответствующих PR. Критерий: описание соответствует коммитам, публичные формы работают при ошибке API.
2. **Назначать владельца каждого изменения.** Оболочка, страница, сессия или remote. Критерий: бизнес-логика каталога и корзины не попадает в app.
3. **Уточнять права при появлении функций.** Перед административными страницами согласовать матрицу доступа и контракт роли. Проверить гостя, USER, ADMIN, прямой URL и отказ backend.
4. **Не возвращать лишние обёртки.** Отдельные route-adapters, query-client, remote-props, load-remote, use-session и pages/remote уже объединены с владельцами логики. Новый файл оправдан самостоятельной обязанностью, повторным использованием или облегчением чтения.
5. **Делить крупные модули по мере роста.** Если подключение новых remote перегрузит router, вынести RemoteRoute. Если появятся несколько самостоятельных правил доступа, выделить guards. Сейчас небольшие компоненты оставлять рядом с деревом маршрутов. Не делать переносы только ради количества строк или папок.
6. **Поддерживать поведение проверками.** При изменении авторизации проверять прямые ссылки, ошибки API, потерю сессии и смену пользователя. При изменении ответственности модулей обновлять архитектуру и это руководство.

Это последовательность дальнейшей работы; перечисленные будущие шаги не считаются выполненными автоматически.

## Проверки и завершение

Для изменений кода из apps/shell:

```powershell
npm run typecheck
npm run check:architecture
npm run build:local
```

При изменении авторизации дополнительно из integration: npm run test:auth. Это браузерные сценарии с контролируемым API без базы данных; они не заменяют проверку реального backend при изменении серверного контракта.

Для Markdown проверить пути, соответствие коду, UTF-8 и git diff --check. Перед commit просмотреть diff и включить только изменения задачи. В PR описать проблему, итоговое поведение, фактические проверки и ограничения. Последующие коммиты той же задачи отправлять в его ветку. Историю задач хранить в Git/PR; руководство описывает устройство проекта и рабочий процесс.
