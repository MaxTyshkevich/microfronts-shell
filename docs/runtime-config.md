# Зачем Shell нужен runtime-конфиг

`runtime-config.json` — обычный JSON-файл с публичными настройками подключения. Shell получает его HTTP-запросом перед запуском React-приложения.

```json
{
  "schemaVersion": 1,
  "apiBaseUrl": "/api",
  "remotes": {
    "catalog": "http://localhost:5174/remoteEntry.js",
    "cart": "http://localhost:5175/remoteEntry.js"
  }
}
```

Здесь `schemaVersion` обозначает формат конфигурации, `apiBaseUrl` — адрес запросов к backend, а `remotes` — точки входа микрофронтов. Это пример локального окружения; production-сборка требует HTTPS для remote.

## Что происходит при открытии сайта

1. `src/main.tsx` вызывает `readConfig` из `app/config/runtime-config.ts`.
2. Браузер запрашивает `/runtime-config.json` с `cache: no-store`.
3. Shell проверяет версию схемы, тип адреса API, протоколы remote и совместимость с HTTPS-страницей.
4. `createApp` регистрирует адреса catalog/cart в Module Federation, создаёт router и providers.
5. При переходе на страницу загружается соответствующий микрофронт. Ему передаются API и контекст сессии, но не полный конфиг Shell.

Если конфиг не удалось получить или проверить, показывается «Ошибка конфигурации». Это дополнительная обязательная зависимость запуска. Настройки читаются один раз при загрузке страницы, а не непрерывно.

## Зачем отдельный файл

Shell должен знать, откуда загружать микрофронты. Локально это порты 5174/5175, на сервере — адреса опубликованных сборок. Отдельный JSON позволяет заменить эти адреса без изменения JavaScript-бандла, если инфраструктура умеет отдельно доставлять конфигурацию. Например, можно переключить каталог на новую совместимую версию, сохранив сборку Shell.

Это не обязательное требование FSD или Module Federation. Можно было читать `import.meta.env` прямо в коде и при смене адресов пересобирать Shell. Такой вариант проще, если отдельное развёртывание конфигурации не требуется. Здесь JSON сохраняет возможность отделить настройки окружения от бандла.

## Что реально реализовано сейчас

| Режим | Кто создаёт JSON | Когда учитываются переменные окружения |
| --- | --- | --- |
| `npm run dev` | Middleware в `vite.config.ts` | При запуске dev-сервера |
| `npm run build` / `build:local` | Vite `generateBundle` записывает `dist/runtime-config.json` | При сборке |
| Docker / Nginx | Nginx отдаёт файл, скопированный из build-stage | Значения уже записаны при сборке образа |
| Render static | Хостинг отдаёт файл из `dist` | При сборке сайта |

**Runtime относится к моменту чтения в браузере. Сейчас генерация production-конфига происходит при сборке.** В Docker нет startup-скрипта, который превращал бы переменные контейнера в JSON. Поэтому изменение `VITE_CATALOG_REMOTE_URL` при запуске готового контейнера ничего не изменит.

Чтобы использовать один образ для разных окружений без пересборки, нужно либо подключить готовый JSON вместо `/usr/share/nginx/html/runtime-config.json`, либо добавить генерацию файла при старте. Эту отдельную задачу текущий FSD-рефакторинг не выполняет.

`API_PROXY_TARGET` — другой вид настройки: это адрес backend для Vite proxy на сервере разработки. Он не попадает в JSON браузера. В контейнере proxy настраивается через `nginx.conf`.

## Практические ограничения

- JSON доступен любому посетителю. Пароли, токены и секретные ключи здесь не хранятся.
- Замена конфига применяется при следующей загрузке страницы. Открытые вкладки продолжают использовать уже прочитанные адреса.
- `no-store` отключает сохранение ответа конфигурации; кэширование JavaScript микрофронтов настраивается отдельно.
- Замена URL не делает несовместимый remote совместимым. Нужно сохранять контракт props и совместимость shared-зависимостей.
- Текущая проверка конфига проверяет основные поля и URL remote, но не заменяет полную JSON Schema-валидацию всех полей.
